# Этап 1. Проектирование доменной области

## 1.1 Бизнес-контекст

Финансовый трекер расходов предназначен для частных пользователей, которые хотят вести учёт личных финансов. Система помогает фиксировать доходы и расходы, распределять их по категориям, поддерживать несколько кошельков в разных валютах, видеть аналитику по месяцам и категориям, а также формировать отчёты для печати или передачи.

Целевая аудитория состоит из двух групп. Первая группа это работающие люди, которые ведут общий семейный бюджет и пользуются банковскими приложениями. Им важно держать все траты в одном месте, разделять личные и общие расходы. Вторая группа это студенты и фрилансеры с переменным доходом. Им нужен простой инструмент, который покажет, на что фактически уходят деньги.

Система решает несколько практических задач. Она хранит историю всех операций по счетам пользователя. Она помогает понять структуру расходов, чтобы найти статьи, на которые уходит больше всего. Она позволяет планировать бюджет на месяц через сравнение факта и плана. Она формирует регулярные сводки для самоконтроля.

## 1.2 Основные сценарии использования

Система поддерживает несколько типовых сценариев. Все они соответствуют практике личного учёта финансов.

Регистрация и вход. Новый пользователь регистрируется по электронной почте и паролю. Затем он входит в систему и получает токен доступа, действующий двадцать четыре часа.

Управление профилем. Один пользователь может иметь несколько профилей. Например, личный профиль и общий семейный. Профили помогают разделять данные, не заводя для этого отдельных аккаунтов.

Управление категориями. Пользователь видит набор системных категорий, общий для всех. Он также может создавать собственные категории внутри профиля, переименовывать их и менять иконки. Удаление невозможно для системных категорий и для тех, которые уже использованы в операциях.

Управление кошельками. Пользователь заводит кошельки для каждого источника или счёта. Кошелёк имеет валюту, начальный баланс и заметку. Кошельки можно архивировать, чтобы убрать из списка, но не потерять историю.

Учёт операций. Это основной сценарий системы. Пользователь добавляет операцию определённого типа, указывает кошелёк, сумму, дату и при желании категорию. Поддерживаются три типа операций: доход, расход и перевод между кошельками. Для этого сценария установлен повышенный уровень надёжности, описанный далее в нефункциональных требованиях.

Просмотр аналитики. Пользователь видит сводку по месяцам и по категориям. Сводка показывает доходы, расходы и итоговый баланс.

Генерация отчёта. Пользователь заказывает отчёт за выбранный период. Заявка ставится в очередь и обрабатывается в фоне. После завершения пользователь может скачать готовый файл.

Кроме пользовательских сценариев есть административные. Администратор управляет системными категориями, добавляет новые и редактирует существующие. Также система раз в сутки самостоятельно обновляет курсы валют, обращаясь к открытому источнику.

## 1.3 Разбиение на сервисы

Система разделена на четыре микросервиса, каждый отвечает за свою предметную область.

Сервис пользователей хранит учётные записи, проверяет пароли, выдаёт токены доступа и ведёт профили. Он не знает о категориях, кошельках или операциях.

Сервис категорий хранит общие системные категории и пользовательские категории. Он отвечает на запросы других сервисов о том, существует ли категория и кому она принадлежит.

Сервис операций самый загруженный. Он хранит кошельки, валюты и сами операции. Он связывается с сервисом пользователей, чтобы убедиться, что профиль существует, и с сервисом категорий, чтобы проверить категорию. Также этот сервис ежедневно скачивает курсы валют.

Сервис отчётов принимает заявки на отчёт, ставит их в очередь и обрабатывает в фоне. Для построения отчёта он обращается за данными к трём другим сервисам, собирает их вместе и сохраняет готовый файл на диск.

Помимо четырёх основных сервисов есть вспомогательный сервис на Python для построения графиков, который используется при формировании отчётов.

## 1.4 Сущности

Каждый сервис имеет свой набор сущностей. Сущности разных сервисов связаны между собой логически, но не через внешние ключи на уровне базы данных. Логическую целостность обеспечивает прикладной код через межсервисные вызовы.

Пользовательская часть состоит из двух сущностей. Учётная запись содержит электронную почту, хэш пароля, имя, фамилию и телефон. Профиль принадлежит учётной записи, имеет название и признак активности.

Категории представлены одной сущностью. У категории есть название, тип операции, к которой она относится, иконка и признак системной. Если категория пользовательская, у неё указан профиль владельца.

В сервисе операций три сущности. Валюта содержит трёхбуквенный код, название, номинал и текущий курс к рублю. Кошелёк принадлежит профилю и имеет название, валюту, начальный баланс, порядок сортировки и признак архивности. Операция принадлежит кошельку, имеет тип, сумму, дату, описание и необязательную ссылку на категорию. Если тип операции это перевод, то указывается также кошелёк назначения.

Сервис отчётов хранит сущность заявки на отчёт. У неё есть тип отчёта, текущий статус, ссылка на пользователя, параметры в виде строки, ключ файла после завершения и поле для текста ошибки.

## 1.5 Связи между сущностями

Логические связи между сущностями отражают бизнес-правила системы. Один пользователь владеет несколькими профилями. Один профиль владеет несколькими кошельками и собственными категориями. Кошелёк ведётся в одной валюте. К каждому кошельку относится много операций. Если операция это перевод, то у неё есть два кошелька, источник и назначение. Категория классифицирует операции. Заявка на отчёт принадлежит пользователю.

Ниже представлены диаграммы связей по каждому сервису, построенные через средство визуализации PgAdmin для созданной базы данных. Каждая диаграмма показывает таблицы соответствующей схемы и связи между ними.

```mermaid
__ER__
```

## 1.6 Диаграмма вариантов использования

Диаграмма вариантов использования показывает, какие действия доступны разным пользователям системы. Обычный пользователь имеет доступ ко всем основным сценариям. Администратор управляет системными категориями. Системный таймер отвечает за периодическое обновление курсов валют.

```mermaid
__USECASE__
```

## 1.7 Диаграммы классов

Диаграммы классов представлены отдельно для каждой группы сервисов. Это сделано для удобства чтения, так как общая диаграмма для всех сущностей системы получилась бы перегруженной.

Первая диаграмма посвящена сервису пользователей. Она показывает учётную запись, профиль и два объекта-значения для электронной почты и хэша пароля.

```mermaid
__CLASSUSERS__
```

Вторая диаграмма показывает сервис операций. На ней видны кошелёк, операция, валюта и перечисление типов операций.

```mermaid
__CLASSTX__
```

Третья диаграмма объединяет сервис категорий и сервис отчётов. На ней представлены категория, заявка на отчёт и связанные перечисления статусов и типов отчётов.

```mermaid
__CLASSCATREP__
```

## 1.8 Жизненный цикл заявки на отчёт

Заявка на отчёт проходит через несколько состояний. Начальное состояние называется Pending, что означает ожидание обработки. Когда фоновый обработчик берёт заявку в работу, она переходит в состояние Processing. После успешного построения отчёта заявка получает статус Completed и в ней сохраняется ключ файла. Если построение завершилось ошибкой, заявка попадает в статус Failed и в ней сохраняется текст ошибки. Из конечных состояний переходов нет.

```mermaid
__STATE__
```

## 1.9 Развёртывание

Все четыре микросервиса и вспомогательный сервис графиков работают в одной сети Docker. База данных PostgreSQL также запускается в этой сети как отдельный контейнер. В базе данных используется четыре схемы, по одной на каждый сервис, что обеспечивает логическую изоляцию данных. Каждый сервис при старте применяет свои миграции и сам отвечает за создание таблиц в своей схеме.

Сервис операций обращается к открытому источнику курсов валют один раз в сутки. Это единственное внешнее обращение системы. Все остальные взаимодействия происходят внутри сети.

```mermaid
__DEPLOY__
```

## 1.10 Бизнес-правила

Электронная почта пользователя должна быть уникальной. Пароль хранится только в виде хэша. У пользователя обязательно есть хотя бы один профиль.

Системные категории нельзя удалять и нельзя переименовывать. Пользовательская категория принадлежит профилю и недоступна другим профилям. Категория с привязанными операциями не удаляется.

Сумма операции всегда положительна. Тип операции должен совпадать с типом её категории. Перевод требует наличия второго кошелька и совпадения валют исходного и целевого кошелька. Переводы между кошельками разных профилей не допускаются. На архивный кошелёк нельзя добавить новую операцию.

У кошелька есть валюта, заданная при создании. Начальный баланс задаётся один раз и далее не редактируется.

Заявка на отчёт обрабатывается асинхронно. Из состояния Completed заявка больше не меняется. Скачивание возможно только после завершения. Файл доступен по ссылке, действующей пятнадцать минут.

## 1.11 Нефункциональные требования

Производительность. Время отклика любого запроса на чтение не превышает двухсот миллисекунд при умеренной нагрузке. Время построения отчёта не превышает тридцати секунд.

Уровень обслуживания основного сценария. Создание операции это критичный сценарий, для которого установлен повышенный уровень надёжности. Сценарий должен корректно работать при кратковременных перебоях смежных сервисов. Подробное описание особых случаев и политики устойчивости приведено в разделе по четвёртому этапу.

Безопасность. Все запросы кроме регистрации и входа требуют действительного токена. Токен подписан секретным ключом длиной не менее тридцати двух символов. Пароли никогда не передаются в открытом виде. Логи не содержат паролей или токенов.

Надёжность. Каждый сервис имеет отдельную точку проверки работоспособности. Любое необработанное исключение перехватывается и возвращается в едином формате. Перебои смежных сервисов обрабатываются по разному в зависимости от их критичности.

Технологические требования. Бэкенд написан на C# и .NET 10. Хранилище общее, PostgreSQL 17 с разделением по схемам. Файлы отчётов хранятся локально на диске с возможностью замены на облачное хранилище. Очередь заявок реализована через периодическую выборку, при росте нагрузки заменяется на полноценную систему очередей.

Логирование. Каждый запрос имеет идентификатор корреляции, который проходит сквозь все вызовы и попадает во все логи. Это позволяет связать события из разных сервисов в одну цепочку.

Совместимость. Пользовательский интерфейс на русском языке. Все валюты приведены к рублю как базовой валюте для аналитики.

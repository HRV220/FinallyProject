# Этап 4. Доработка системы и устойчивость

## 4.1 Цель этапа

Целью четвёртого этапа является доработка системы до уровня готового рабочего прототипа. Основное внимание уделено синхронному взаимодействию между сервисами и устойчивости основного сценария создания операции к перебоям смежных сервисов.

Для основного сценария установлен повышенный уровень обслуживания, который описан в нефункциональных требованиях первого этапа. На этом этапе выполнено его инженерное воплощение.

## 4.2 Главный сценарий

Главным сценарием системы является создание операции через метод POST /api/transactions. Этот сценарий вовлекает три из четырёх сервисов и потому особенно чувствителен к их доступности.

Последовательность работы сценария следующая. Клиент отправляет запрос с указанием кошелька, типа операции, суммы, даты, описания и при необходимости категории. Сервис операций сначала проверяет формат данных через валидаторы. Затем он получает кошелёк из своей базы данных и проверяет, что кошелёк существует и не находится в архиве. После этого сервис обращается к сервису пользователей с проверкой того, что профиль кошелька существует и принадлежит автору запроса.

Если операция является переводом, дополнительно проверяется кошелёк назначения. Кошелёк назначения должен принадлежать тому же профилю и быть в той же валюте, что и исходный кошелёк.

Если запрос содержит идентификатор категории, сервис операций обращается к сервису категорий с проверкой существования и принадлежности категории профилю.

Только после успешного прохождения всех проверок операция сохраняется в базу и её идентификатор возвращается клиенту.

Полная диаграмма последовательности приведена ниже. На ней также показаны ветви для всех возможных ошибочных исходов.

```mermaid
__SEQ_SLA9__
```

## 4.3 Особые случаи основного сценария

Для главного сценария разобраны и обработаны двенадцать особых случаев. В каждом из них сценарий должен вести себя предсказуемо. Все случаи сведены в таблицу.

| Номер | Ситуация | Поведение системы |
|---|---|---|
| 1 | Сумма операции превышает один триллион | Возвращается ошибка четыреста с кодом Transaction.AmountTooLarge |
| 2 | Кошелёк по идентификатору не найден | Возвращается ошибка четыреста с кодом Transaction.WalletNotFound |
| 3 | Кошелёк находится в архиве | Возвращается ошибка четыреста с кодом Wallet.Archived |
| 4 | Сервис пользователей ответил четыреста четыре | Возвращается ошибка четыреста с кодом Profile.NotFoundOrInactive |
| 5 | Сервис пользователей недоступен после повторов | Возвращается ошибка пятьсот три с кодом Dependency.UsersUnavailable, операция не создаётся |
| 6 | Перевод без указания целевого кошелька | Возвращается ошибка четыреста с кодом Transaction.TransferRequiresDestination |
| 7 | Перевод на кошелёк чужого профиля | Возвращается ошибка четыреста с кодом Transaction.CrossProfileTransfer |
| 8 | Перевод на архивный кошелёк | Возвращается ошибка четыреста с кодом Wallet.Archived |
| 9 | Перевод между кошельками разных валют | Возвращается ошибка четыреста с кодом Transaction.CurrencyMismatch |
| 10 | Категория не существует | Возвращается ошибка четыреста с кодом Transaction.CategoryNotFound |
| 11 | Категория принадлежит другому профилю | Возвращается ошибка четыреста с кодом Category.NotOwned |
| 12 | Сервис категорий недоступен | Операция создаётся без категории, в журнал пишется предупреждение |

Двенадцатый случай заслуживает отдельного объяснения. Категория не является критически важной частью операции. Если сервис категорий временно недоступен, система предпочитает сохранить факт операции без категории, чем отказать пользователю. Это реализация подхода, который называется деградация с сохранением функциональности.

Сервис пользователей напротив является критически важным. Без подтверждения, что профиль существует и принадлежит автору запроса, операция не может быть сохранена. Поэтому в пятом случае система отказывает в обслуживании с кодом пятьсот три.

## 4.4 Политика устойчивости

Для всех исходящих HTTP вызовов между сервисами настроена общая политика устойчивости. Она построена на стандартной библиотеке Microsoft.Extensions.Http.Resilience, которая под капотом использует Polly версии восемь.

Политика включает несколько слоёв защиты. Каждое HTTP соединение имеет жёсткое ограничение по общему времени. Это защищает от зависших соединений. Каждый отдельный вызов имеет собственное ограничение по времени. При сбое выполняются два повтора с увеличивающейся задержкой. Это позволяет автоматически переждать кратковременные перебои. Сверху работает предохранитель. Если половина или больше последних пяти запросов завершились сбоем, предохранитель размыкается на тридцать секунд. В этот период все вызовы к данному сервису сразу отдают ошибку, не нагружая упавший сервис.

Конкретные значения сведены в таблицу.

| Параметр | Значение |
|---|---|
| Общее ограничение по времени | Десять секунд для большинства, пятнадцать для отчётов |
| Ограничение на один вызов | Две секунды для большинства, пять для отчётов |
| Число повторов | Два |
| Задержка между повторами | Двести пятьдесят миллисекунд с удвоением |
| Тип задержки | Экспоненциальный |
| Порог срабатывания предохранителя | Половина запросов с ошибкой |
| Минимальное число запросов для оценки | Пять |
| Длительность размыкания | Тридцать секунд |

Такая конфигурация даёт хороший баланс между отзывчивостью к временным сбоям и защитой смежного сервиса от каскадного отказа.

## 4.5 Сквозная трассировка через идентификатор корреляции

Для отслеживания запросов через несколько сервисов реализован общий механизм идентификатора корреляции.

При входе запроса промежуточный обработчик читает заголовок X-Correlation-Id. Если заголовок задан клиентом, используется его значение. Иначе генерируется новый идентификатор в формате GUID без разделителей. Этот идентификатор кладётся в свойства текущего HTTP контекста и в область журнала. Затем он возвращается клиенту в ответе.

Когда сервис делает исходящий вызов к смежному сервису, специальный делегирующий обработчик берёт идентификатор из текущего контекста и кладёт его в заголовок исходящего запроса. Принимающий сервис тем же самым промежуточным обработчиком читает заголовок и продолжает цепочку.

В итоге один пользовательский запрос имеет единый идентификатор во всех журналах сервисов пользователей, операций, категорий и отчётов. Это позволяет легко собрать всю цепочку событий по одному поиску.

## 4.6 Единый формат ошибок

Все необработанные исключения перехватываются единым промежуточным обработчиком и возвращаются клиенту в формате RFC 7807. Этот формат называется ProblemDetails и принят как стандарт для представления ошибок HTTP API.

В теле ответа всегда есть поля type, title, status и detail. К ним добавляется расширение correlationId с идентификатором корреляции. Это позволяет пользователю при обращении в поддержку сослаться на конкретный идентификатор, и команда поддержки сможет найти все события этой цепочки в журналах.

В среде разработки в поле detail передаётся полный стек вызовов для упрощения отладки. В рабочей среде передаётся только текст исключения без технических подробностей.

Доменные ошибки остаются прежним механизмом. Они возвращаются через тип Result и преобразуются контроллерами в ответы четыреста, четыреста четыре или четыреста девять в зависимости от смысла ошибки.

## 4.7 Конвейер обработки отчётов

Отчёты в системе строятся асинхронно через фоновый обработчик. Это позволяет не блокировать запросы пользователя и при необходимости масштабировать обработку отдельно от основного API.

Принцип работы следующий. Клиент отправляет запрос на построение отчёта. Сервис отчётов сохраняет заявку в своей базе со статусом ожидания и сразу возвращает идентификатор заявки клиенту. Фоновый обработчик каждые пять секунд проверяет наличие новых заявок. Найденные заявки переводятся в статус обработки. Для каждой заявки параллельно делаются запросы к сервису пользователей, сервису категорий и сервису операций. Полученные данные собираются вместе и из них формируется файл CSV. Файл сохраняется в локальное хранилище, заявка переводится в статус Completed с указанием ключа файла. Клиент по этому ключу может скачать готовый файл.

```mermaid
__SEQ_REPORTS__
```

Локальное хранилище это просто папка на диске, смонтированная как том Docker. Интерфейс хранилища абстрагирует работу с файлами. Это позволяет в дальнейшем заменить локальное хранилище на облачное без изменения остального кода.

Формат отчёта реализован как CSV. Это намеренное упрощение для текущего этапа. Интерфейс генератора отчётов позволяет легко добавить PDF или другой формат, не затрагивая остальной код. Очередь сейчас реализована через периодическую выборку. При росте нагрузки её можно заменить на полноценную систему очередей или библиотеку Hangfire.

## 4.8 Переменные окружения

Адреса смежных сервисов настраиваются через переменные окружения. Это позволяет одному и тому же образу контейнера работать в разных средах без перекомпиляции.

| Сервис | Переменная | Назначение |
|---|---|---|
| Категории | UsersService__BaseUrl | Адрес сервиса пользователей |
| Операции | UsersService__BaseUrl | Адрес сервиса пользователей |
| Операции | CategoriesService__BaseUrl | Адрес сервиса категорий |
| Отчёты | UsersService__BaseUrl | Адрес сервиса пользователей |
| Отчёты | CategoriesService__BaseUrl | Адрес сервиса категорий |
| Отчёты | TransactionsService__BaseUrl | Адрес сервиса операций |
| Отчёты | ReportStorage__Path | Путь к хранилищу файлов |
| Отчёты | ReportStorage__PublicBaseUrl | Базовый адрес для ссылки скачивания |

В файле docker-compose.yml эти переменные заполнены внутренними именами контейнеров. Для запуска вне Docker значения по умолчанию указывают на адреса localhost с соответствующими портами.

## 4.9 Что осталось вне этапа

В рамках четвёртого этапа сознательно не были выполнены некоторые задачи, относящиеся к более поздним стадиям зрелости системы. Это распределённая трассировка через систему OpenTelemetry, полноценные интеграционные тесты с базой данных через библиотеку Testcontainers, замена локального хранилища на облачное, полная реализация PDF отчётов и реализация распределённых транзакций через паттерн саги.

Для каждой из этих задач инфраструктура подготовлена. Замена локального хранилища требует лишь новой реализации интерфейса. Замена CSV на PDF требует лишь нового генератора. Эти точки расширения заложены сразу для упрощения будущей доработки.

# Этап 3. Реализация системы

## 3.1 Архитектура решения

Реализация выполнена на платформе .NET 10 с использованием языка C#. Каждый из четырёх микросервисов оформлен как отдельное приложение в стиле чистой архитектуры. Внутри каждого сервиса выделены четыре слоя.

Слой домена содержит сущности предметной области и бизнес-правила. Это самый внутренний слой, он не зависит ни от каких внешних библиотек кроме базовой платформы.

Слой приложения содержит обработчики команд и запросов, написанные в стиле CQRS через библиотеку MediatR. Каждая команда это отдельный класс с одним обработчиком. Это упрощает чтение и тестирование кода.

Слой инфраструктуры содержит конкретные реализации работы с базой данных через Entity Framework Core, реализации обращения к внешним сервисам через библиотеку Refit и регистрацию политики устойчивости через библиотеку Microsoft.Extensions.Http.Resilience.

Слой API содержит контроллеры, которые принимают HTTP запросы, передают их в обработчики и формируют ответы. Также этот слой содержит настройки приложения и точку входа.

Кроме четырёх сервисов реализованы общие компоненты. Они вынесены в проект Core.Domain, содержащий базовый класс сущности, обёртку для результата операции и тип доменной ошибки. Также есть проект Core.Infrastructure, содержащий промежуточные обработчики для идентификатора корреляции и единого формата ошибок.

Для построения графиков отдельно реализован сервис на Python с использованием библиотек FastAPI и Matplotlib. Этот сервис принимает данные и возвращает готовое изображение.

## 3.2 Структура решения

Решение оформлено как файл нового формата FinanceTracker.slnx. Это позволяет работать с проектом в любой современной интегрированной среде разработки.

Каждый сервис организован в отдельной папке, внутри которой находятся четыре проекта по числу слоёв. Например, сервис пользователей лежит в папке src/Users и содержит проекты Users.Domain, Users.Application, Users.Infrastructure и Users.API. Аналогично устроены сервисы категорий, операций и отчётов.

Общие компоненты лежат в папке src/BuildingBlocks. Сервис графиков лежит в папке ChartService.

## 3.3 Хранилище данных

Все четыре сервиса используют одно общее хранилище PostgreSQL версии 17, но разделение проходит по схемам. Сервис пользователей пишет в схему users, сервис категорий в схему categories, сервис операций в схему transactions, сервис отчётов в схему reports.

Такой подход позволяет сохранить логическую изоляцию данных без поднятия отдельной базы под каждый сервис. При необходимости каждая схема может быть вынесена в отдельную базу или даже на отдельный сервер без изменения кода сервиса.

Схемы создаются автоматически при первом запуске базы данных из скрипта db-init/01-create-schemas.sql. Этот скрипт исполняется контейнером PostgreSQL до того, как сервисы получат соединение.

После создания схем каждый сервис при своём старте применяет миграции Entity Framework Core. Миграции создают и поддерживают набор таблиц только своей схемы. Поскольку у каждого сервиса своя таблица истории миграций, сервисы не мешают друг другу.

## 3.4 Запуск через Docker Compose

Все сервисы упакованы в контейнеры. Файл docker-compose.yml описывает порядок запуска и связи между контейнерами.

Сначала поднимается контейнер базы данных. После того как база готова принимать соединения, запускается сервис пользователей. После него запускается сервис категорий, который зависит от пользователей. Затем сервис операций, который зависит от пользователей и категорий. И последним сервис отчётов, который зависит от всех остальных. Параллельно запускается сервис графиков на Python.

Каждому сервису через переменные окружения передаётся строка подключения к базе и адреса смежных сервисов. Адреса используют внутренние имена контейнеров, которые разрешаются через встроенный DNS Docker.

Для запуска достаточно скопировать файл .env.example в файл .env, при необходимости отредактировать значения и выполнить команду docker compose up build. Первая сборка занимает около пяти минут из-за загрузки образов и компиляции.

## 3.5 Аутентификация и авторизация

Аутентификация реализована через токены формата JWT. Сервис пользователей при входе формирует токен, подписывая его секретным ключом. Все остальные сервисы используют тот же ключ для проверки подписи. Это позволяет любому сервису проверить токен без обращения к сервису пользователей.

В токен включены идентификатор пользователя, его электронная почта и время истечения. Срок действия токена двадцать четыре часа.

Защищённые методы помечены атрибутом, требующим действительного токена. Открытые методы помечены отдельным атрибутом, разрешающим анонимный вход. К открытым методам относятся регистрация и вход.

## 3.6 Валидация данных

Входные данные каждого запроса проходят два уровня проверки. Первый уровень это валидация через библиотеку FluentValidation. Она проверяет формат, длину и обязательность полей до того, как запрос попадает в обработчик.

Второй уровень это доменная валидация внутри сущностей. Например, метод создания операции проверяет положительность суммы и соответствие типа операции типу её категории. Такие проверки нельзя обойти даже если запрос прошёл первый уровень.

Результат операции возвращается через тип Result. Этот тип позволяет описать успех с данными или ошибку с кодом и сообщением, без использования исключений как механизма управления потоком.

## 3.7 Особенности реализации сервисов

Сервис пользователей при первом старте создаёт системные роли и проверяет наличие администратора. Пароли хэшируются с использованием алгоритма BCrypt.

Сервис категорий при первом старте создаёт набор системных категорий. Например, продукты, транспорт, развлечения, коммунальные платежи. Эти категории доступны всем пользователям без возможности изменения.

Сервис операций при первом старте создаёт справочник валют. Также этот сервис содержит фоновую задачу, которая раз в сутки обращается к открытому источнику курсов валют и обновляет справочник. Источник это XML-фид Центрального банка Российской Федерации.

Сервис отчётов содержит фоновую задачу для обработки заявок. Эта задача каждые пять секунд проверяет наличие заявок в состоянии ожидания и берёт их в работу. Для каждой заявки она получает данные от смежных сервисов, формирует файл CSV и сохраняет его в локальное хранилище. Затем заявка переходит в состояние Completed с указанием ключа файла.

Для хранения файлов отчётов используется отдельная папка, монтируемая как том Docker. При замене на облачное хранилище меняется только реализация интерфейса IFileStorage, остальной код не затрагивается.

## 3.8 Проверка работоспособности

Каждый сервис предоставляет метод health для быстрой проверки работоспособности. Этот метод возвращает короткий ответ с подтверждением того, что сервис запущен. Этот метод используется системой оркестрации Docker для определения готовности сервиса к приёму запросов.

Для проверки сценария от начала до конца составлен набор команд curl. Он включает регистрацию нового пользователя, вход с получением токена, создание профиля, получение системных категорий, получение валют, создание кошелька и операции, заказ отчёта и его последующее скачивание.

## 3.9 Документация и навигация

Каждый сервис автоматически генерирует документацию по своим методам в формате OpenAPI и предоставляет интерактивный обозреватель по адресу /scalar. Это позволяет разработчику или тестировщику без дополнительных инструментов изучить интерфейс сервиса.

Внутренняя навигация по коду организована через стандартное именование. Команды лежат в папке Commands, запросы в папке Queries. Внутри каждой команды три файла: сама команда, её обработчик и валидатор. Контроллеры именуются по сущности, к которой они относятся.
